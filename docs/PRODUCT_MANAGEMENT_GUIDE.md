# 用 Moyu番茄钟学产品经理

## 你真正要训练的能力

产品经理不是“写很多文档的人”，而是持续降低四种不确定性：为谁做、解决什么、先做什么、怎样算做成。这个项目的文档只为这四个问题服务。

## 1. PRD：统一决定，而非堆砌愿望

PRD（Product Requirements Document）记录可执行的产品决定。`PRD.md` 中的 T04 是范例：“工作完成只自动进入休息，不进入下一段工作”。这句话同时约束开发、测试和界面文案。

练习：把“提醒我什么时候工作”改写成一个能判断通过/失败的句子。避免“体验好、速度快、智能”等无法直接验收的词。

## 2. MVP：先验证最重要的价值链

MVP（Minimum Viable Product）不是粗糙版，也不是功能越少越好。Moyu 的价值链是：看见时间 → 完成一段专注 → 得到休息提醒 → 愿意再次开始。任务和统计可以增强产品，却不是验证这条链的必要条件。

练习：挑一个你想添加的功能，写出“没有它，哪条核心用户流程就无法成立？”无法回答时，先放入后续候选。

## 3. 用户故事：从人的处境解释需求

格式：“作为［某类用户］，我希望［做什么］，以便［获得什么价值］。”重点在最后的价值。它防止团队只交出一个按钮，却不知道为什么需要它。

练习：将“要猫咪”写成用户故事。比较“缓解单调陪伴感”和“更可爱”两种目的会怎样改变动效克制程度。

## 4. 原型：用低成本暴露理解差异

网页 Demo 是交互原型，不是原生 App。它验证布局、视觉、信息层级和流程；它不能证明 macOS 置顶、系统通知、签名安装包可用。

原型确认时，按以下顺序：核心流程是否正确 → 信息是否看得懂 → 操作是否顺手 → 风格是否喜欢。不要只评论颜色。

## 5. 验收标准：提前约定“完成”

好验收包含动作、条件和结果。例如：“暂停后等待 2 秒，剩余时间不变；重开页面仍显示同一剩余时间。”坏验收：“暂停功能正常。”

PRD 的编号不是为了显得正式，而是让需求能追踪到实现与测试，防止遗漏。

## 6. 需求追踪：从一句话走到证据

链路：用户故事 → PRD 编号 → 界面/逻辑 → 自动或人工测试 → 验收结论。`TRACEABILITY.md` 将保留这条链，未测试的项目不能标成已完成。

## 7. 技术选型：产品经理需要理解取舍

- React：把界面拆成组件，适合快速迭代网页原型。
- TypeScript：给状态与设置加类型，减少“把字符串当数字”等错误。
- Vite：开发服务器和打包工具，负责本地预览与生产构建。
- SwiftUI：苹果声明式界面框架，负责正式 macOS 界面。
- AppKit：更底层的 macOS 窗口能力；悬浮窗置顶、缩放等由它补足 SwiftUI。
- Playwright：用真实浏览器执行点击、截图和断言，不是仅靠人工查看。

本项目网页与原生界面复用的是 PRD、设计规则和计时行为，不强行复用两套 UI 代码。

## 8. 版本号：向用户表达变化和风险

语义化版本为 `主版本.次版本.修订版本`：破坏性变化升主版本，向后兼容的新功能升次版本，修复升修订版本。`v0.1.0-beta.1` 表示仍在早期公开测试，不等于稳定 v1.0.0。

## 9. 发布：不是把文件传上去

发布包括版本内容、可复现构建、测试证据、安装说明、已知限制、许可证和回滚意识。未签名、未公证、未实测的包必须明确标注，不能用“完成发布”掩盖安装风险。

## 10. 你的第一轮产品复盘作业

看完 Demo 后，用自己的话回答：

1. 第一眼先看到了什么？它是否是最重要信息？
2. 开始计时需要几步？哪一步是多余的？
3. 猫咪何时可爱、何时干扰？你会怎样调整，而不是笼统说“再可爱点”？
4. 哪三个需求构成你愿意使用的最小版本？哪一个可以删掉？
5. 选择一个不满意点，写成“用户故事 + 验收标准”。

这就是产品经理的日常：观察、取舍、定义、验证，再迭代。
